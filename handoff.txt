Developer Handoff Package: Online Product Catalog and Sales Management System
Nov 18, 2026 · @Omor
The approved design is sound and buildable, but 8 gaps must be closed before coding starts; this package lists the fixes, then gives backend, database and frontend developers one set of specs and 11 diagrams.
1. Design review
Verdict: approve with changes. Nothing needs a redesign; all 31 findings below are additions or clarifications, and the rest of this package already uses the proposed fixes. A fix marked proposed is not approved until you confirm it in section 11.
What checked out
Counts match the text: 8 modules, 11 tables, 45 endpoints (auth 7, users 3, products 8, stock 3, customers 5, reports 8, targets 3, dashboards 8).
Every table has exactly one owning module, and modules touch each other&apos;s data only through service calls.
Wireframe arithmetic is correct: 35,000 of 50,000 is 70% with 15,000 remaining; 960 + 825 = 1,785; 480 × 2 = 960.
The state diagrams match the endpoints, and the stock ledger rules are consistent (sale and sale_returned require a report_id).
Money as NUMERIC, ON DELETE RESTRICT, client submission keys and price snapshots on report lines are sound.

2. Locked conventions
Every team builds to the rules below; they close findings F-01, F-05, F-15 to F-18, F-20 and F-30. Items marked (proposed) need your sign-off in section 11.

Time zone
Stored as UTC TIMESTAMPTZ. COMPANY_TZ = Asia/Dhaka (proposed). report_date = the COMPANY_TZ calendar date of first submission; month parameters (YYYY-MM) and today are read in COMPANY_TZ.

Login: verify the password first; only then return ACCOUNT_PENDING, ACCOUNT_REJECTED or ACCOUNT_DISABLED. Unknown identifiers run a dummy hash check and return INVALID_CREDENTIALS. 10 failed attempts a minute per IP and identifier returns 429.

Business rules every module shares
Visible product or variant = product.is_active AND variant.is_active. Reports can only contain visible variants of active customers.
Variant in_stock = quantity &gt; 0. Product in_stock = any visible variant in stock. Sales users never see quantities.
Only approved reports count. They count toward the month and day of report_date, not of the approval date.
Progress % = floor(approved ÷ target × 100), not capped. Remaining = max(target − approved, 0); exceeded = max(approved − target, 0); waiting = sum of submitted reports in that month.
On resubmission: status = submitted, submitted_at = now, reviewed_by, reviewed_at and reject_reason cleared, report_date unchanged, items replaced (decision A of F-06).
The password-reset response is always the same generic 200, whether or not the email exists.

6. Database
PostgreSQL holds 11 tables with BIGINT identity keys, UTC TIMESTAMPTZ audit columns and ON DELETE RESTRICT on every foreign key.

ER diagram · 11 tables, 11 foreign-key links
The two highlighted tables are the ones every report touches: sales_reports for the sale, stock_movements for the ledger entry.
Changes against the source schema (all proposed, each tied to a finding)
users.phone becomes UNIQUE and canonical (F-02, F-11); users gains password_changed_at (F-05).
Trigram GIN indexes on users.full_name, products.name, customers.name and customers.phone (F-19).
Sync indexes on products and customers by (updated_at, id), and triggers that touch products.updated_at on variant or image changes (F-04, F-20).
stock_movements gets sign checks by reason (F-23); sales_reports gets status-consistency checks and a partial index for the approval queue.
sales_report_items keeps DELETE for the app role, because a resubmission replaces the lines (F-06, option A). If you choose option B, add report_events and drop this exception.
Migration order: 1 extension and roles; 2 users; 3 password_resets; 4 products; 5 product_variants; 6 product_images; 7 stock; 8 customers; 9 sales_reports; 10 sales_report_items; 11 stock_movements; 12 monthly_targets; 13 triggers and grants.

8. Backend
The backend is eight modules under /backend/app/modules/, each with router, schemas, service and repository files; routers never touch another module&apos;s tables, they call its service functions.
State machines

user account states · 4 states, 5 transitions
A pending or rejected account cannot log in; disabling takes effect on the account&apos;s next request because status is read on every call.

sales report states · 3 states, 5 transitions
Approval changes nothing in stock. Reject, reverse and resubmit are the only moves that do, and each runs in one transaction.
Submission sequence

sequence · POST /reports, 4 participants, 8 messages
The same order of work is used for PUT /reports/{id}, minus the idempotency lookup. Step 3 comes before the reads in step 4 so that a price or visibility check can never be stale (F-03).

Transaction recipes. Lock order everywhere: the sales_reports row first, then stock rows by ascending variant_id. Never take them in another order.
Submit (#27): find (user_id, submission_key), return 200 if found; BEGIN with lock_timeout 5 s; lock stock rows; read customer, variants and products FOR SHARE and check visibility and prices; check quantities; update stock; insert movements (sale, negative); insert report with report_date = today in COMPANY_TZ, and items with copied name, size and price; compute line and grand totals on the server; COMMIT.
Resubmit (#28): lock the report row, require status rejected and the caller as owner; delete its items; then repeat steps 2 to 6 of the submit recipe; set status submitted, submitted_at = now, clear reviewed_by, reviewed_at and reject_reason; keep report_date and submission_key.
Approve (#31): lock the report row; require submitted; set approved, reviewed_by, reviewed_at. No stock change.
Bulk approve (#32): sort ids; run recipe 3 per report in its own transaction; collect skipped ids with their code.
Reject or reverse (#33): lock the report row; require submitted or approved; lock stock rows ascending; restore quantities; insert sale_returned movements (positive); set rejected, reviewer, time and reason; COMMIT; then send the report-rejected email.
Adjust stock (#21): lock the stock row; require quantity + change at least 0, else STOCK_BELOW_ZERO; update; insert a movement with the note.
Add variant (#15): insert the variant and its stock row at 0 in one transaction.
Set user status (#10): lock the user row; check the transition table in section 2 and the self and last-admin guards (count active admins FOR UPDATE); update; send the email after commit.

Security checklist
Passwords: Argon2id; the reset token is random, emailed once and stored only as a SHA-256 hash; 1 hour expiry, single use.
Rate limits: login 10 failed attempts a minute (key: IP plus identifier); forgot-password and register also limited.
CORS allows only the app origin; HTTPS only with HSTS; a strict Content-Security-Policy on the PWA; no third-party scripts.
Uploads: Pillow verifies the file, applies EXIF rotation, caps pixel count, fits inside the square on white, writes WebP under UUID names, discards the original.
Exports: sanitize text cells that start with =, +, -, @, tab or carriage return; write phone numbers as strings (F-22).
Data access: SQLAlchemy parameters only, no string-built SQL; DB role limits as in section 6; no personal data in logs.

offline sync flow · 7 steps, 1 decision
Offline PWA contract
Cached for offline reading: the active catalog with 200 by 200 thumbnails and the active customer list. Nothing else works offline, and S5 is disabled with a clear message.
Store catalog and customers in IndexedDB and thumbnails in CacheStorage (Workbox). Show a last-synced time next to In Stock, because stock status is only as fresh as the last sync (F-04).
Sync on login (full), on every app open and on reconnect (delta). Customer deltas return hidden rows as {id, is_active: false}; remove them locally. Follow next_cursor until null and save server_time only after the last page.
Wipe everything on logout and on 403 ACCOUNT_DISABLED, and clear the token on 401.
Optional: wipe after 14 days with no successful online check (F-31, open question 8).
Report builder rules
Create a submission_key (UUID v4) when the draft starts. Keep it across retries; make a new one only for a new draft.
Take unit_price from the cached catalog and show it read-only. On 409 PRICE_CHANGED, replace the prices from details, show the change and let the user submit again with the same key.
Limits: 50 distinct variants, quantity 1 to 100000 per line, no duplicate variants (add to the existing line instead).
Totals on screen are for display; the server&apos;s totals win.
Disable the submit button while a request is in flight. On a network timeout, retry with the same key; on STOCK_SHORT or OUT_OF_STOCK, show the available quantity from details.
For a rejected report, open S5 with its items and show the reject reason on top; resubmitting calls PUT, and a REPORT_NOT_EDITABLE reply carrying an equal report counts as success (F-10).
Client architecture and UI rules
Server state with TanStack Query; routes with React Router; forms validated against the same limits as the API; the error envelope maps fields to inputs, and request_id is shown as a reference in error toasts.
API client: adds the Bearer token, sends X-Request-ID, handles 401 and 403 as above, formats money from strings without float math.
Layout: sales screens designed for 360 px wide phones with 44 px touch targets and a bottom bar of Home, Catalog, New report, Reports; admin screens for desktop with a left sidebar and sticky table headers.
Every list has loading, empty and error states. Status chips: submitted, approved, rejected. Destructive actions (reject, reverse, disable) ask for confirmation.
